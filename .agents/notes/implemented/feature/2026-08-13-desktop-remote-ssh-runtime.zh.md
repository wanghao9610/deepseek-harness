# Agent Note：桌面外壳经 SSH 由远程主机提供其运行时

Status: implemented

[English](2026-08-13-desktop-remote-ssh-runtime.md) | 中文

## Problem

桌面外壳监管的运行时就在窗口所在的机器上，因此 agent 只能在那台机器上读文件、跑命令、开终端。要在另一台机器上工作，就得彻底放弃这个外壳——改用 SSH 会话加终端界面——或者把远端运行时的 HTTP 服务暴露到一个它并没有认证能力的网络上。

当时有两种现成形态，而它们都不是人们说"远程开发"时指的东西。把端口转发到一个别人手工启动的运行时，会把它的生命周期、就绪判定与失败诊断都留在应用之外。而在 SSH 之上重新实现文件系统与子进程缝，只会搬走可变世界，却搬不走对面本就原生具备的语言服务器、终端、沙箱与进程监管。

## Decision

运行时既可以由本机提供，也可以由一台经 SSH 访问的主机提供；而**是哪一种，是交给 supervisor 的那次启动的属性，不是监管本身的属性。** `RuntimeSupervisor` 按每次 start 而非每个 supervisor 准备一次启动，因为远程启动每次都占用一对新端口，也因为人可能在上一次之后换了主机。

远程运行时就是远端的一整套 harness。文件、命令、终端、语言服务器、会话、凭据——没有任何一项被适配：桌面应用只保留窗口与连接列表。同一次 `ssh` 会话既启动那个运行时，又把它的回环端口转发回来，因此窗口加载的是一个普通的回环 origin，API 客户端、引导界面与提醒流都无需改动。

`@deepseek-ai/dsh-ssh-launch` 是 `packages/boot/` 下的一个纯库，与其他启动器粘合层为邻。它做规划与校验，不启动任何进程。`apps/desktop` 负责派生该计划、分配本地回环端口，并持有重启节奏。"连接"这件事之所以归外壳，是因为 Electron 主进程不是 Cordis context，也因为一个用来选择"连哪个 runtime"的客户端插件，必须由它尚未连上的那个 runtime 来提供。

### 连接属于窗口

正在使用的每条连接各有一个运行时，在某个窗口首次请求它时创建，而每个窗口只显示**它自己那条连接**正在做什么。最初的安排是整个应用一个运行时：把任意一个窗口指向某台主机，会停掉其他每个窗口正在观看的那个运行时，并把它们全都推到同一个等待界面上——而这不是开第二个窗口的目的。位于同一条连接上的窗口仍然共用一个运行时，因此常规情形没有变化。

窗口离开某条连接时不拆除任何东西。仍被其他窗口使用的运行时继续提供服务，而最后一个窗口离开的那个运行时就没有属于自己的窗口了——这恰好是空闲规则度量的东西，因此它按既有策略停止，而不需要一条关于"切换"的新规则。已存的选择成为之后新开窗口的默认值，而不是对当前已打开窗口的更改。

### 等待不是死路

每个等待中的界面都带有自己的操作，按 Escape 等同于 Stop。首次连接会在主机上安装启动器，这要花上几分钟；而该界面最初发布时只在失败状态下才有按钮，于是那次安装除了强制退出没有别的出口。

停止能触及进程存在之前的工作。准备阶段——读取归档、探测主机、发送负载——拿到的是 supervisor 持有的中止信号，因此取消会结束那次传输，而不是把它留在一个已经离开的窗口背后继续跑。被取消的准备汇报为"已停止"而非"失败"，因为那正是人所要求的。

### 一次启动持有什么

`RuntimeLaunch` 携带命令行，以及两种启动之间有差异的三个答案：

- **在哪里访问运行时。** 本地那种就在它自己打印的地址上访问。远程那种打印的是它在自己主机上绑定的地址，而只有被转发的端口能被外壳访问到，因此该次启动会做映射——并拒绝其他任何地址，因为重启修不好一个正在本机看不见的地方提供服务的运行时。这种拒绝是致命的，而不是又一次重启尝试。
- **如何停止它。** 本地运行时收到 `SIGTERM`。远程运行时则通过关闭 `ssh` 会话的 stdin 来请求停止：远端脚本会在对面把它转成同样的 `SIGTERM`。改为向 `ssh` 发信号会让运行时成为孤儿，因为 sshd 早已把它从通道上分离了。
- **失败意味着什么。** `ssh` 把每一种远端侧失败都报告为它自己的退出状态，因此诊断读的是输出——被拒绝的密钥、无法解析的主机、缺失的远端启动器——supervisor 为此保留一段有界的输出尾巴。

### 远端脚本双向监管

两个方向都无法从对方推出，因此交给账户 shell 的脚本两件事都做：它把运行时放到后台、等待它、以它的状态码退出，同时由一个 shell 内建的 read 在 stdin 关闭时结束运行时。用内建很关键——辅助进程被杀死后仍会占着会话的 stdin，会话也就关不掉。

因此调用方必须在运行时的整个生命周期内为该脚本保持 stdin 打开；stdin 为 `/dev/null` 的启动会在运行时刚起来的瞬间把它结束掉。这层耦合写在启动上（`stdin: 'pipe'`、`stopsOnStdinEnd`），而不是留给一条注释。

### 每条连接一个服务端根目录

某条连接在主机上接触到的一切都位于同一个根目录之下——除非连接另行指定，否则是 `~/.dsh-server`。安装物位于 `bin/` 下、按连接所请求的内容作用域，而该根目录会作为运行时的 `DSH_HOME` 导出，因此会话、storages、设置与 preset 都落在它们旁边。删掉那一个目录就抹掉了每一次访问的痕迹——这正是该布局存在的理由。

### 主机不必事先有启动器，也不必有 registry

一条连接要么指明主机自带的启动器，要么让外壳从 npm 装一份，要么接收本机持有的那一份；三者互斥，而三个都不指明就得到那次从 registry 的安装。一次悄悄找错 `dsh` 的 `PATH` 查找，比一份由外壳持有的副本更糟；而受管启动器完全不看账户的 `PATH`，这正是它能在非交互登录 shell 没有 `PATH` 的主机上工作的原因。

安装是同一段远端脚本的前置部分，而不是另一次会话，因此供给与启动是一次认证、一条连接，两者中任一失败都经由 supervisor 已经在处理的那一条路径到达。**启动器存在就是全部检查**：目录按所请求的版本作用域，因此之后的连接不需要 registry、也不需要网络，并且没有任何东西会自行升级——改变某条连接所请求的版本，才是移动那台主机的动作。版本名被校验到路径安全的字母表，这正是脚本可以不加引用地把它插进路径的原因；路径在对面推导，因为只有对面知道 `$HOME` 在哪。

**没有网络的主机改为接收一份负载。** 从 registry 安装无法服务气隙主机，因此连接可以指向一个本地归档，由外壳把它流式送进一个负责解包的 `ssh`——两台机器上都不落临时文件，用的也是与到该主机的其他每条命令相同的连接选项。

这条路带着一个 registry 路径没有的约束：**负载只能在它被构建的那个平台上运行。** 它携带的 closure 含已编译原生模块，其中的 `node-pty` 被 `dsh-subprocess-local` 在模块加载时静态导入——因此在别处构建的负载意味着一个根本起不来的运行时，而不是一个降级运行的运行时。于是外壳在发送任何字节之前先问主机是什么，与"是否已经带有这份负载"在同一次往返里问完，并拒绝不匹配。构建负载是 `pnpm run package:remote-server`，它标注自己构建出的是什么，而不接受目标参数：它运行所在的那台机器是它唯一能产出的平台。

负载替代的是 registry，不是 Node。它不自带运行时，因此启动仍保留 registry 路径所用的同一处 Node 检查。它的启动器是包自身的入口而非 `node_modules/.bin/dsh`：部署出的 closure 是一棵依赖树，不是一次 npm 安装，根本没有 bin 目录。

版本默认取 `latest` dist-tag，而不是外壳自身的版本。钉住外壳版本是更强的保证，也是 VS Code 对其 server commit 的做法，但本外壳的版本并不保证已发布——`0.1.0-rc.5` 发布时 registry 上只有 `rc.3` 与 `rc.6`——而一个解析到不存在版本的默认值，就是一个永远不工作的功能。而且这里的版本偏移比看上去更便宜：浏览器的整套 UI 都从远端运行时加载，因此本地对远端的契约只有就绪行、profile 标志，以及外壳订阅的那两条事件下行流。

安装要花上几分钟，因此前置部分用一个前缀播报自己的步骤、由外壳读进引导界面；它也把自己能指认的失败——没有 Node、Node 太旧、没有 npm、安装失败、安装后没有启动器——作为退出状态给出。这些是仅有的、其含义无需从输出文本中还原的失败。

### 校验就是执行点

一条连接的每个字段都会到达 `ssh` 参数或远端登录 shell，而设置文件与表单都是人书写的边界。校验拒绝的是那些会改变命令**含义**而非参数的取值：以 `-` 开头的 host、user 或跳板机——`ssh` 会把它读成选项，其中包括在外壳自己机器上执行命令的 `ProxyCommand`——以及出现在任何位置的控制字符。通过校验的取值仍要引用，因为 sshd 交给 shell 的是一个字符串，而不是参数向量。

`BatchMode=yes` 属于同一姿态：窗口化外壳没有可用来回答提示的终端，因此需要提示的连接会带着诊断失败，而不是无限等待。代价是无法使用口令与密钥短语认证。

### 转发带来的两个事实

远端运行时看到的是一次 SSH 启动，因此它的自适应目录选择器会解析为应用内浏览器，而不是试图在一台无人值守的机器上弹出系统选择器。以及，请求是从 `127.0.0.1` 到达远端 `/api` 的——这正是那些特权方法（目录选择、设置、凭据、preset 授权）仍然可用的原因：在真正的认证层出现之前，它们只对回环开放。两者都源于走隧道而不是绑定网络接口，而这也是 web 服务器文档中唯一认定安全的姿态。

## Alternatives considered

**在 SSH 之上实现 `ctx.fs` 与 `ctx.subprocess`，把 harness 留在本地。** 否决：它搬走了可变世界，却搬不走对面本就原生具备的东西，而这两个缝之上的每一项能力都要付适配代价——远端 PID 与前台进程组探测、每个语言服务器和终端各占一个通道带来的 `MaxSessions` 压力，以及活动句柄无法重连。[可移植执行世界的决策](../architecture/2026-07-28-portable-execution-world-consumers.md)持有那个缝；把整套 harness 跑在对面正是它明确排除在外的部署模型，而当主机能运行 `dsh` 时，这条路更便宜。

**把"连接"做成客户端插件。** 在当前结构下否决为不可实现：客户端插件包由 runtime 经 HTTP 提供，因此一个用来选择"连哪个 runtime"的插件，必须由它尚未连上的那个 runtime 来提供。VS Code 用 UI/workspace 扩展二分解决这一点；本客户端没有这样的二分，而发明一个比这项功能本身还大。

**让人自己选远端端口，或先探测一个空闲端口。** 否决：在运行时绑定之前没有任何办法证明某个远端端口空闲，而一次探测往返只会把竞态窗口缩小。从动态范围内抽取、并把冲突当作可重试的启动失败，复用的是已经在处理本地冲突的那条路径。

**强制分配 pty，让远端运行时随会话一起死。** 否决：pty 会改写承载就绪行与日志的那条流。stdin 看门狗在不碰输出的前提下达到同样的结果。

**用向 `ssh` 发信号来做优雅停止。** 否决：那结束的是载体而不是运行时，会在每次断开后于对面留下一整套常驻 harness。

**把受管启动器钉死在外壳自身的版本上。** 作为默认值被否决，因为外壳的版本并不保证已发布，而一个解析到缺失版本的默认值就是一个永远不工作的功能。连接仍可以钉任意版本——同样的机制，只是没有那个会坏掉的默认值。

**在启动之前用另一次 `ssh` 会话做供给。** 否决：它为同一条连接把认证与失败面都翻倍，还会拆散 supervisor 本已知道如何汇报的那份诊断。放在同一段脚本的前置部分只需一次会话、一条路径。

**每次连接都刷新受管安装。** 否决：它让一台本来能用的主机每次使用都依赖 registry 与网络，只为在那一刻交付一次没人要求的升级。按版本作用域目录，使升级成为一次显式编辑，并让已安装的主机可以离线使用。

**把桌面应用内嵌的那份 closure 拷到主机上。** 作为通用答案被否决，并作为最终落地方案的约束保留下来：那份 closure 是按外壳自身平台构建的，而 mac 外壳连 Linux 主机正是常见组合。可行的是为主机构建的负载——这也正是构建器要标注平台、外壳要拒绝不匹配的原因。

**在连接时于外壳所在机器上构建负载。** 否决：打包后的应用不携带 Node 也不携带包管理器——那份自包含正是打包的意义所在——因此它无法为任何平台产出 closure，更不用说另一个平台。负载是一个人产出一次的构建产物。

**探测主机并自动选择传输方式。** 否决：两种传输方式的差别不只是快慢，还在于人需要事先准备什么：从 registry 回退到负载，需要一份没人构建过的归档。由连接说明用哪一种，而每种失败都会指明该改什么。

## Consequences

远程开发的代价是一个库加外壳里的一个分支。对面的每一项 harness 能力都是发布出去的那一个，因此对终端、语言服务器或沙箱的修复不需要远程对应实现，而窗口、通知、Dock 角标与内存策略都照常工作。

外壳现在依赖 OpenSSH 客户端，也依赖主机要么自带启动器、要么能安装一个——后者意味着 Node 22.19 或更新版本以及 npm。认证只支持 agent 或密钥文件。内存策略在远程时不再度量运行时——子进程是 `ssh` 会话，其常驻内存说明不了 harness 的任何情况——因此只有空闲规则适用于它。

有一种失败模式仍在外壳够不到的地方：stdin 看门狗在 sshd 关闭通道时触发，这需要 sshd 察觉客户端已消失。`ClientAliveInterval` 默认关闭，因此一条没有发出 TCP FIN 就被切断的链路，会让远端运行时一直等到 TCP keepalive 到期。

## Testing

包级测试固定了校验规则（含对选项形状与控制字符的拒绝、路径安全的版本字母表，以及既非绝对路径也非 `~/` 开头的服务端根目录）、参数向量、三种形态的远端脚本、探测与传输计划、转发地址映射、进度读取器，以及每一条诊断。桌面测试用一个"会报告地址、并在 stdin 关闭时结束"的替身载体来驱动 supervisor，采用的是真实的远程启动、只替换其命令行：它们证明窗口被送往转发端口、停止走的是关闭 stdin 而不是发信号、缓慢启动会显示它正在做什么并在运行时开始服务后停止显示，以及一个本机无法访问的地址会失败且不重启。引导界面在 jsdom 中按外壳实际发送的载荷渲染验证。

远端脚本本身在登录 shell 中针对真实启动器（而非替身）在两条供给路径上都做过验证：没有安装的主机会执行 npm 安装并发出外壳所读取的进度、已供给的主机跳过安装并启动真实运行时、关闭 stdin 会停止它且不留下进程、自行退出的运行时会透传状态码。负载路径针对 `package:remote-server` 产出的归档做过验证：清单与摘要能被读回、探测能报告主机并拒绝异平台、传输会解包并改名就位、解开的运行时能提供服务并被停止。

**在多个 shell 下运行该脚本是这项验证的一部分，而不是额外项。** 最初落地的看门狗直接读 fd 0，这在 `zsh` 下能用，在 `sh` 与 `bash` 下会坏：关闭作业控制的 shell 会在处理显式重定向之前把异步命令的 stdin 指向 `/dev/null`，于是看门狗立刻读到文件结束，杀掉了它本该守护的运行时。修复是把会话的 stdin 留在一个复制出的描述符上，而验证的地方正是远程账户可能拥有的每一种 shell。

CI 没有覆盖这一块，原因与桌面应用已记录的一致：驱动外壳需要窗口会话，而一次真实连接需要第二台主机。
