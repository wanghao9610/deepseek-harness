# Agent Note: keyboard shortcuts in the Web client

Status: implemented

English | [中文](2026-08-13-client-keyboard-shortcuts.zh.md)

## Problem

The Web surface reaches its two most frequent operations — opening Settings and starting a new Session — through one control each, in the sidebar column. Both are things a person does between turns, with their hands already on the keyboard, and neither had a chord. The desktop shell cannot supply one: its window loads the harness UI as ordinary web content with no preload, so a menu accelerator there would take the key and have nowhere to send it ([the desktop application note](../architecture/2026-08-13-electron-desktop-application.md)).

## Decision

The chords live in the client, on the component that already owns the operation. `SettingsRoot` binds `⌘,` / `Ctrl+,` to its own `open` state, `SidebarRoot` binds `⌘K` / `Ctrl+K` to the `startSession` callback it already renders two buttons for and `⌘B` / `Ctrl+B` to `toggleSidebar`, and `WorkspaceBrowser` binds `⌘O` / `Ctrl+O` to the add-workspace state behind its section-header button and `⇧⌘F` / `Ctrl+Shift+F` to its search. Nothing is lifted: the operation's owner is its shortcut's owner, so a chord cannot outlive or contradict the control beside it.

A chord inherits its control's availability, not just its action. The add button renders only while the surface's directory-flow hole is occupied, so `⌘O` reads the same occupancy: over an empty hole the press does nothing, rather than arming a picker state that a later-mounting occupant would raise with no gesture behind it.

Where a control's two column states reach the operation differently, the chord takes each state's own route rather than a third one. `⌘B` toggles rather than collapses, because the rail has no second key to come back with and the button under it is the same one in both states. The search chord reveals the box in the wide column and, from the rail, arms the focus and asks the shell to expand — what the rail's own control does, because the box exists only in the wide column.

`useShortcut` in `dsh-client-ui-primitives` is the one piece they all share. It binds one document-level chord, and it owns the platform choice: Command on Apple platforms, Control everywhere else, read from the user agent. Accepting either modifier would be simpler and wrong — macOS gives Control+letter to text editing inside every field (`Ctrl+K` deletes to end of line), and Windows gives Meta+letter to the desktop shell. A chord is either a bare key or `{ key, shift }`, and Shift is part of its identity in both directions: a chord that wants Shift is not answered without it, and a chord that does not is not answered while it is held. The hook rejects a press carrying the other platform's modifier, an Alt (macOS composes characters with it), a Shift the chord did not ask for, and a held key's repeats; it calls `preventDefault` so the browser does not also act on the key, and it reads the action through a ref so a caller needs no `useCallback`.

A chord acts wherever focus is, the composer included, because a modifier means the keystroke was never text the user meant to type. `⌘K` and `⌘B` act in both sidebar states, since they belong to the column rather than to either button; `⌘O` and `⇧⌘F` likewise, since the browsing region fills the column in both states. `⌘,` on an open panel leaves it open on whichever section is showing.

Each control announces its chord on hover and on keyboard focus, through `shortcutLabel` — the platform read's other half, which writes `⌘K` or `Ctrl+K`. The New Session tooltip reads `New session ⌘K` and now rides both column states rather than the rail alone, because the chord is the one thing the expanded button's own label does not carry. The add-workspace, search, and collapse buttons already had tooltips naming their actions, so each appends its chord — `Add workspace ⌘O`, `Search ⇧⌘F`, `Collapse sidebar ⌘B` under either of that button's two labels — with the accessible names left as the actions alone. The settings trigger, which had no tooltip at all, shows the chord by itself: that shell is a composition face holding no copy, and the slot system's `label` option — how the nav rows carry a registrant's words — exists on list slots, while `settings.trigger` is a single one.

Because the desktop shell's menu takes any accelerator it claims before the page can see it, these chords are a contract between the two layers rather than a client-local choice. The desktop menu test holds all five and rejects a menu item that would claim any of them. It is also what caught `⇧⌘O`, the obvious chord for adding a workspace: the shell's own Open in Browser already holds it.

## Alternatives considered

- **Desktop menu items driving the page.** The macOS convention puts Settings in the app menu under `⌘,`, and a menu item is the one keyboard map a user can read. It needs a route from the shell into the harness UI — a preload the desktop note already rejected on sandbox grounds, or `executeJavaScript` against a hook the page would have to expose. Both make the shell a participant in UI operations it otherwise knows nothing about, and neither reaches `dsh web` in a browser, where the same chords have to work.
- **A shortcut registry service in the client.** One plugin owning a keymap would give the client what `menu.ts` gives the shell: a single readable map with collision detection. It needs every action lifted out of the component that owns it — the settings panel's `open` state most of all — and `⌘O` arrived without needing that: the third chord repeated the same one-line pattern in a third package and collided with nothing. What a registry answers is the question this design cannot: whether two client packages have claimed the same key, which today only a reader comparing four files can see. The client-versus-shell half of that question is covered — the desktop menu test caught `⇧⌘O` against Open in Browser — and it is the half with a gate precisely because the shell's map is one object. The client's is not, and the next chord is what keeps paying for that.
- **A bare `⌘F` for search.** The chord every application uses for finding things in itself, and in a browser tab it is the reader's find-in-page — the one keystroke a page should not take from them. `⇧⌘F` is where an editor puts searching its own content, and Shift is also what lifts a chord out of the space browsers have already claimed.
- **`metaKey || ctrlKey`, with no platform read.** Half the code and the common shortcut in web apps. It fires on macOS `Ctrl+K` inside a text field, which is a text-editing keystroke there, and it makes the map's own definition depend on what the user happened to hold.
- **Naming the action in the settings tooltip too.** Symmetry with `New session ⌘K` costs the settings shell its one rule: either the slot options widen so a single slot can carry a registrant's `label` for the shell to resolve, or the shell reads the `settings` dictionary directly and becomes a second source for text the trigger seat already renders. The chord alone is what that shell can say while owning no words.
- **Binding the chords in the layout shell instead.** One home for all of them, and the layout is always mounted. It reaches neither operation without new props threaded from two other packages, and the sidebar column is not conditionally mounted either.

## Consequences

- The chords work in `dsh web` and in the desktop application from the same code, except where the browser's own menu bar outranks the page. On macOS, Chrome answers `⌘,` with its settings and `⌘O` with its Open File dialog before the page is offered either key, so both reach the harness UI only in the desktop window, where nothing claims them. `⌘K`, `⌘B`, and `⇧⌘F` have no such competitor. The asymmetry is macOS-specific: menu-bar chords are resolved by the application there, while Windows and Linux browsers let the page take all but a small reserved set.
- Every chord is discoverable from the control it acts on, and the settings trigger gained the tooltip it never had — which is also the first accessible hint on that button in the collapsed rail, where its seat renders an icon and no text.
- The desktop shell and the client now share a keyboard map with no common source: the client binds `,`, `k`, and `o`, and the desktop menu test restates all three to keep the shell off them. A client shortcut added without that test entry can be silently shadowed on the desktop.
- `useShortcut` grew an optional Shift, which is the only expansion the map needed: bare `⌘`+letter is nearly exhausted by the browsers themselves, while `⇧⌘` is mostly free of them. Alt stays rejected — macOS composes characters with it.
- `useShortcut` reads `navigator.userAgent`. A browser that hides or spoofs the platform gets the Control spelling.
