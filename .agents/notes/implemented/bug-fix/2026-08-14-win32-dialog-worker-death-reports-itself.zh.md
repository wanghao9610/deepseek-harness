# Agent Note: win32 对话框子进程死亡时会说明原因

Status: implemented

[English](2026-08-14-win32-dialog-worker-death-reports-itself.md) | 中文

## Problem

已安装的 Windows [桌面应用](../architecture/2026-08-13-electron-desktop-application.md)中，工作区选择器以 `directory picker failed: directory picker failed: win32 folder dialog worker exited before reporting a result` 失败。

这句话就是产品知道的全部。[对话框驱动](../feature/2026-08-02-win32-in-process-folder-dialog.md)手里握有关于这个已死子进程的三项事实——退出码、信号，以及它打印的一切——却一项都没写进拒绝原因：`exit` 被处理成 `() => reject(...)`，标准错误则被继承进宿主自己的标准错误，而在打包应用里那是 `%APPDATA%` 下一个用户不会打开、任何错误消息也不会引用的日志文件。加载期抛出、COM 会话内部的原生访问违例、以及在模态调用之下被关闭的 IPC 通道，三者产生的正是这同一句话，而唯一能把它们区分开的就是退出码。前缀之所以重复出现，是因为 Host RPC 与它的 Consumer 各自都点了一次操作名，于是对话框仅有的一行消息，开头被同一件事占用了两遍。

它失败在那条没有任何测试覆盖的路径上。源码平面有一条真实 Windows 冒烟测试，并且通过；打包平面——运行完整 COM 会话的打包 CJS worker——从未在任何测试下跑过，[对话框记录](../feature/2026-08-02-win32-in-process-folder-dialog.md)已把这一点记为已知缺口。那条未测路径上躺着两个缺陷，成功选择所经由的返回路径上还有第三个。

## Decision

子进程若在上报结果前死亡，现在会带着它如何结束、以及它说了什么一起拒绝。标准错误改为管道而非继承，`pickWin32Directory` 保留其有界尾部；拒绝原因经 `describeExit` 点明结束方式，并附上该尾部。Windows 把原生故障报告为 NTSTATUS 取值的退出码，因此 POSIX 状态范围之外的退出码同时携带其十六进制形式——`0xc0000005` 指明访问违例，而 `3221225477` 什么也没指明。驱动改为在 `close` 而非 `exit` 上落定：`exit` 可能早于子进程最后一块标准错误到达，而那一块恰恰是解释加载期抛出的那一块；除 worker 外无人持有该管道，因此它的结束总会关闭管道。

随之修复了这条路径上的三个缺陷。

**只有结果消息才关闭 IPC 通道。** worker 的 `post` 在发送每条消息时都挂了一个断开连接的完成回调，而它自己的 `disconnect` 处理器会退出进程——于是 `showing` 通知（其后紧跟一个用户浏览多久就运行多久的模态调用）在自身之下埋了一次拆解。`post` 现在只负责发送；另设的 `finish` 发送结果并随后关闭通道。

**COM 字符串终止于零码元，而非零字节。** `readUtf16` 按字节扫描，因此码点为 0x100 整数倍的字符——U+4E00 一 即在其中——会提前结束路径：`C:\项目一号\src` 返回成了 `C:\项目`。选择器悄无声息地返回了一个用户并未选择的目录，任何地方都不会报错。

**Host RPC 只上报原因本身。** 每个 Consumer 都会自行点明失败的操作，而这个响应本就是对某一个请求的回答。

构建产物守卫现在会在 win32 上驱动打包 worker 走完一次真实对话框——打开、`showing`、关闭对话框线程的窗口，并断言结果依然抵达——而不再跳过它本就为之存在的平台。它断言的是结果而不仅是打开，因为一个在通知与结果之间死亡的 worker，对停在通知处的测试是不可见的。

## Alternatives considered

**先诊断出 Windows 上的失败，只修那一个原因。** 根据产品给出的证据无法确定机制：三者的消息完全相同，而能区分它们的退出码正是驱动丢弃掉的东西。复现需要 Windows 上的打包应用，而这里没有任何流水线能构建并运行它。先修可证之处、其余改为自我说明，能立刻得到一个正确的改动，并从下一次发生中拿到确切原因，而不是把猜测当作修复发布出去。

**保留继承的标准错误，改去读桌面运行时日志。** 原因今天其实已经写在那里——日志本就是这样设计的。但它同时也是一个遭遇失败的人并不知道其存在的文件，需要别人告知路径才能找到，而他们真正看见的那句消息依旧什么都没说。需要第二份产物才能成立的诊断，对用户而言就不是诊断；而这次失败首先是用户的，其次才是维护者的。

**在 `exit` 上落定，标准错误收到多少算多少。** 更简单，却恰恰在要紧的那种情形下是错的：加载期抛出前的最后一块，通常正是 `exit` 触发时仍在途中的那一块，于是拒绝原因会在它最有话可说的时候恰好为空。

**保留单一的 `post`，让它在每条消息后都断开。** 这次拆解是潜在的而非必然的——模态调用阻塞了事件循环，完成回调无法在结果发出之前运行——但它在一个仍在进行中的操作之下埋了一次进程退出，而这条路径的时长恰恰取决于一个人浏览文件系统有多久。一种仅仅因为事件循环碰巧被什么阻塞着才安全的生命周期，不该在追查一个具有此种特征的失败时被留在原地。

**子进程死亡时回退到另一种选择器机制。** [链路移除记录](../simplification/2026-08-04-drop-windows-powershell-picker-fallback.md)已经否决过一次，这次因同样的理由再次否决：它把一次可上报的失败变成一次无声的降级。组合层面的回退仍是 browse 后端。

## Consequences

- 对话框子进程若在上报结果前死亡，会点明其结束方式并引用它打印的内容，因此下一次 Windows 反馈将指认机制，而不是复述症状。
- 途经零低位字节字符的中文及其他非 ASCII 路径现在能完整返回。此前任何在被截断路径上打开的工作区，打开的都是用户没有选择的目录。
- 打包 worker 的 COM 会话在 win32 上获得覆盖，补上了[对话框记录](../feature/2026-08-02-win32-in-process-folder-dialog.md)所点明缺口中属于打包 worker 的一半。该守卫需要带桌面的真实 Windows 会话，因此由自托管 Windows 流水线运行。
- 该缺口的另一半原样保留：打包**可执行文件**把自身作为对话框入口再次启动——即以 `ELECTRON_RUN_AS_NODE` 模式运行的 Electron 而非 `node`——仍然没有任何测试覆盖，因为没有流水线打包桌面应用。该启动方式经人工确认能加载打包 worker、解析 koffi 并携带 IPC 通道；至于一台 Windows 机器会在此之上带来什么，仍属未测。
- Host 的 `pickDirectory` 错误消息即原因原文。不点明操作名的 Consumer 将展示裸的原因。
