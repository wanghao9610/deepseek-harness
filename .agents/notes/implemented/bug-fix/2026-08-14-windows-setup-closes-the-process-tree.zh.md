# Agent Note: Windows 安装器关闭整棵进程树，闭包只装入可加载的文件

Status: implemented

[English](2026-08-14-windows-setup-closes-the-process-tree.md) | 中文

## Problem

覆盖安装到一个正在运行的安装目录上，要花好几分钟，然后以"DeepSeek Harness 无法关闭。请手动关闭它，然后单击"重试"以继续。"告终。两个彼此独立的原因汇合成了这一条消息。

electron-builder 检测应用是否在运行时，会找出可执行文件路径位于安装目录下的每一个进程，逐个终止，并在两轮强制终止后放弃——大约六秒。而本应用始终不止一个这样的进程：外壳通过 `ELECTRON_RUN_AS_NODE` 用自己的可执行文件启动 harness 运行时，于是运行时带着外壳的映像名与路径；运行时以 detached 方式启动，外壳被终止后它仍然存活；监督器还会把已服务满一分钟的运行时零延迟重启。先终止运行时，外壳会在下一次扫描前补上一个新的；先终止外壳，detached 的运行时留在原地。无论安装器先够到哪一个，紧随其后的扫描仍会找到一个，六秒预算随即耗尽。

这些幸存进程占住的文件接着让旧版卸载器失败，而安装器最多重跑它五次才报出同一条消息。这是耗时的后半段。

前半段是负载本身。闭包过去装入 25,490 个文件，其中超过一半是它自己无法加载的：9,804 个 TypeScript 声明、2,243 个第三方源码、854 个文档文件。Windows 安装的节奏由逐文件解压和每个写入文件的实时扫描决定，远甚于总字节数，所以决定时长的是文件数，不是那 524 MiB。

## Decision

### 安装器关闭整棵进程树

[`apps/desktop/build/close-app-processes.nsh`](../../../../apps/desktop/build/close-app-processes.nsh) 定义 `customCheckAppRunning`——app-builder-lib 会用它替换自带的检测——打包脚本把它作为 NSIS `include` 指定。

终止是无条件的。先探测、仅在探测为真时才动手的检查，一旦探测命令自身失败就会整个跳过关闭动作——一次静默的空操作，其症状正是它本该阻止的那个故障——而终止"什么都没有"的代价只是一条报告无匹配的命令。探测仍然执行，但它决定的是要不要询问用户，而非要不要动手。

每一轮以两种方式匹配进程。`taskkill /F /T /IM` 让每个映像名匹配连同其子进程一起结束，于是存活的外壳会带着运行时以及它启动的那些 shell 一起结束。随后一轮 PowerShell 终止可执行文件位于安装目录之下的任何进程，这够到了那些原生宿主与 pty 辅助进程——它们既不带应用的名字，在其父进程消失后也不再处于任何可从应用出发到达的进程树中。预算是 20 轮、每轮 500 毫秒，而不是约三秒内的两轮。

该宏自带 PowerShell 探测。默认检测的 `$IsPowerShellAvailable` 只在被本宏替换掉的那个分支里初始化，复用那个宏的 `FIND_PROCESS` 无法通过编译。安装器与卸载器既不带应用的映像名，也不位于安装目录之下，所以任何一轮都不会终止正在运行它的安装器。

对用户在应用运行时主动发起的安装，该宏保留确认提示，并在 `isUpdated` 下跳过，与它替换掉的行为一致。它的标签带有逐次插入的后缀，因为 NSIS 把安装器与卸载器编译为同一个脚本，两者各插入该宏一次。

### 闭包只装入它能加载的东西

[`scripts/package-desktop-app.ts`](../../../../scripts/package-desktop-app.ts) 里的 `pruneClosure` 删除每一个 `.ts`、`.mts`、`.cts` 文件——包括声明文件——连同 source map、文档 Markdown，以及由此清空的目录。

闭包里没有任何东西能加载它们。那里不装入任何 TypeScript 工具链——没有 `typescript`、`tsx`、`esbuild` 或 `@swc/core`——所以 Node 从不读取 `types` 导出条件；而 windows-acl runner 只有在构建产物 `lib/runner.js` 缺失时才通过 `tsx` 去取源码，打包始终提供该产物。source map 随它们指向的源码一起删除。

Markdown 按文档词干裁剪，并在 `config` 或 `assets` 目录下豁免。skill 加载器会读取 skill 目录下的每一个 `.md`，所以那里出现的文档词干命名的是一个 skill 而非一篇文档；随包装入的 Cordis 预设与徽章正文恰好位于这些位置。

流水线在体积旁边一并报告文件数，因为 Windows 安装的节奏正由这个数字决定。

### 三个位置抛出同一条消息

`appCannotBeClosed` 是三处彼此不同的失败所共用的文案，而本宏只拥有其中一处。安装前检查就是这里被替换掉的那处。`uninstallOldVersion` 在旧版卸载器连续五次返回非零时抛出它。`extractAppPackage` 则在对已安装目录树执行的 `CopyFiles` 连续五次失败（每次间隔一秒）时抛出它——那时进度条已经在走，而 Retry 按钮会落到一段就地覆盖、忽略逐文件错误的 `Nsis7z::Extract`，所以回答 Retry 会以非原子的方式装完。

因此，对这条消息的报告必须先指明它出自哪个阶段，才谈得上指认原因：只有第一处才可能是安装前那一轮漏掉的进程，另外两处意味着某个文件是在那一轮跑完之后才被占用的，或者根本不是被某个进程占住的。

## Alternatives considered

**在安装器运行期间挂起运行时的自动重启。** 监督器无法把安装器的 `TerminateProcess` 与一次崩溃区分开，所以这个方案唯一诚实的形态是由安装器置位、外壳读取的一个开关——一套新的跨进程协议，其失败模式是运行时再也无法从真正的崩溃中恢复。杀整棵树不需要任何这类约定。

**给运行时一个自己的可执行文件名。** 换个名字就能让安装器关闭外壳而不匹配到运行时。但运行时需要 Electron 的 Node——即 `--expose-internals` 这条通往内部 ES 模块加载器的路径，因为 `node-addon-require-builtin` 插件在 Electron 下无法加载——所以它必须从 Electron 二进制启动。改名的副本会多出一个 215 MiB 的可执行文件，并且在 macOS 上落在本流水线所施加的 ad-hoc 签名之外。

**把闭包做成一个由安装器解开的归档。** NSIS 要写的文件会少得多。但 Electron 既不能从归档内部导入 ES 模块，也不能加载原生插件——正是排除 asar 的同一约束——所以归档只能在首次运行时展开，把代价转嫁到用户的第一次启动，并让卸载无法交代自己写下过什么。

**保留声明与源码以便现场调试。** 本次改动之前 source map 就已被裁剪，栈追踪本来就只指向构建产物；保留下来的源码没有任何可以单步跟踪的东西。

## Testing

一次 macOS 打包运行会用与出厂外壳相同的命令行启动裁剪后的闭包并读取其提供的页面，这正是"裁剪没有删掉运行时会加载的任何东西"的证明。Windows 安装器在本机编译，因而证明了 NSIS 脚本能够装配，打包后目录树的文件数也是直接测得的。

关闭路径本身未经证明：Windows 版 Electron 二进制无法在 macOS 上运行，所以本机没有任何一次运行会走到该宏。要证明它，需要在 Windows 上对一个正在运行的应用做一次覆盖安装。

## Consequences

一次 Windows 安装写入 12,504 个文件而非 25,490 个，安装器为 126.4 MiB 而非 137.6 MiB。解包后的目录树从 524.3 MiB 降到 482.9 MiB——只占收益的一小部分，而这正是要点：文件数减半，字节数几乎没动。

安装器强制终止正在运行的应用，而不是请求它退出。会话是持久的，且 Windows 本就把监督器的 `SIGTERM` 映射为 `TerminateProcess`，所以这与平台自身关停路径所采取的是同一类停止；那条路径上同样不会运行任何 disposer。

日后若有任何东西需要在运行时读取 `.ts` 文件或一个以文档词干命名的 `.md`，必须把它加进 `pruneClosure` 的豁免里，而 Windows 安装在相应代码路径实际运行之前不会暴露这个遗漏。
